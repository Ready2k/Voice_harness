02 / THE TWO PATHS

Actions and audio
follow separate checks.

A service can propose a banking action or produce audio. The harness handles each through a distinct controlled path.

01

Action path

A tool proposal reaches the orchestrator and guardrail before the synthetic bank. Identity and confirmation checks govern whether a protected action can proceed.

02

Audio path

Audio is held in approval units. Independent transcription and assessment inform the policy decision before the playback gate releases it.

03

Separate outcomes

The assessment distinguishes service behaviour from the protection supplied by the harness. A blocked misstatement can still be a service failure.

03 / EVIDENCE AND ASSESSMENT

Keep the record.
Expose the unknowns.

Checks and evidence are designed to support investigation, including when a result cannot be assessed.

THE EVIDENCE TRAIL

From events to a verifiable bundle.

Runs write to an append-only, hash-chained ledger. Exports include signed manifests that can be verified offline against a trusted key ring.

Deterministic checks

04 / RUN LIFECYCLE

From request
to recorded outcome.

A live run binds a scenario and provider configuration, opens a session, then records both the interaction and its assessment.

01queuedPOST /api/v1/runs
02probingAvailability and capability binding
03runningProvider session and turns
04evaluatingAssess retained evidence
05completedAssessment and assurance recorded

Timeouts, adapter errors and judging errors can fail a run; queued, probing and running states can be cancelled. Cancellation emits no completed event, assessment or assurance. The ledger remains the source of truth.

SCENARIO INPUT

Speech into the adapter

LiveScenarioRunner synthesises the caller and sends audio in 20 ms chunks. The adapter translates between provider-specific transport and the harness event contract.

TURN HANDLING

Events into controlled paths

AdapterTurnDriver routes tool calls through the guardrail and MCP gateway, and audio through the approval buffer and playback gate.

PROVIDER BOUNDARY

Canonical events

LiveAdapter emits closed events for audio, transcripts, tool calls, turn boundaries, interruption, usage and errors; original provider payloads are retained.

05 / ENFORCEMENT PATHS

Two paths.
Two control boundaries.

Tool execution and audio playback are separate decisions. These paths show where the harness applies its controls.

01 / ACTION

Before a synthetic bank action

  1. Provider tool proposal
  2. Orchestrator
  3. Guardrail
  4. MCP gateway
  5. Synthetic bank

Protected proposals are denied before execution unless identity and confirmation state permit them. Approval tokens and confirmations are single-use and consumed transactionally. Bank state is isolated per run; tool results return through the adapter.

engine.py · guardrail.py · approvals.py · mcp_gateway.py · bank.py

02 / AUDIO

Before sound reaches the client

  1. Provider audio
  2. Approval buffer
  3. ASR + assessment
  4. Policy + gate
  5. Client scheduler

Pending PCM approval units are immutable and bound to session, hash, range and epoch. Independent ASR and assessment inform the policy decision; the playback gate releases approved audio and records each release. Input audio has no direct route to output.

playback.py · asr.py · live_assessment.py · policy.py · apps/web/

Evidence-write failure blocks tool calls and releases. AI judge signals are advisory under the current policy; judges do not directly mutate banking state or release audio.

06 / ASSESSMENT AND EVIDENCE

What is checked.
What can be proven.

Assessment separates provider behaviour from enforcement: a blocked incorrect statement remains a service failure even if the control contained it.

DETERMINISTIC CRITERIA

Defined checks

IDENTITY-01, FACT-01, CONFIRM-01, AUDIO-01 and SCENARIO-PROPOSAL-01 apply according to each scenario. CARE-01 requires a judge.

FACT-01

Independent spoken facts

Independent ASR text is compared with tool results and reference facts, including amounts, dates and identifiers bound to their entity and field.

RESULTS

Four dispositions

pass, fail, untestable and not_applicable distinguish outcomes. Unresolved evidence is not a pass, and missing audio is not automatically inapplicable.

EVIDENCE EXPORT / TRUST CHAIN

  1. Run events
  2. Hash-chained ledger
  3. Manifest + hashes
  4. Ed25519 signature
  5. Offline verification

Manifests use RFC 8785 canonical JSON and include event counts, final and artifact hashes, provider coverage, cost and retention information. The verifier requires a trusted key ring obtained out of band. Retention purges are recorded as tombstones; restricted reviewer exports are separately signed and linked by hash.

python -m voice_harness verify-bundle BUNDLE --public-key KEYRING

AI judges are opt-in, independence-checked and calibrated on a synthetic holdout. No AI blocking policy is approved; synthetic calibration is not human validation.

Common commands

make up          # API and collector
make demo        # mock scenarios + bundles
make test        # PostgreSQL + browser tests
make lint        # ruff + bandit
make serve-live  # host API for live providers

Local development uses SQLite; Compose uses PostgreSQL. Live provider calls are opt-in and require credentials. The default synthetic caller uses macOS speech tools; openai_tts is an opt-in alternative.

Known boundaries

Mock fixture audio is silence: tests exercise enforcement mechanics, not recognition accuracy. Audio alignment, reconnect/resume and direct MCP remain unknown for every provider. Synthetic noise and narrowband shaping are not measured telephony. Private signing keys are stored on disk rather than in a KMS or HSM.

Provider support is derived from an adapter, a valid capability report and a passing AC-09 result bound to that report. Unexercised features remain unknown; consult the source for current provider-specific status.
